# Complete REST API Design - Lecture Notes

## 1. Introduction & The Goal of API Design
* **The Core Problem:** Backend developers, especially early in their careers, face recurring questions such as:
  * Should URI paths be singular or plural? [2]
  * When updating, should you use `PUT` or `PATCH`? [2]
  * Which HTTP method should be used for custom (non-CRUD) actions? [2]
  * Which HTTP status codes apply to specific scenarios? [2]
* **The Solution:** Establish and adhere to consistent, industry-standard API guidelines [3]. Sticking to these guidelines allows development teams to eliminate guesswork, reduce bugs, speed up integrations, and focus directly on core business logic rather than constantly debating API semantics [4, 40].
* **Interface First:** API design is an interface-design task, not an implementation task [38, 101]. It should be completed before writing any business logic or choosing a programming language [38, 101].

## 2. History of REST and Web Scalability
To design good REST APIs, it is essential to understand the architectural crisis that birthed the standard.

### 2.1 The Scalability Crisis (1990–1993)
* **1990:** Tim Berners-Lee invented the World Wide Web project to facilitate global knowledge sharing [5]. Within a short period, he invented **URIs**, **HTTP**, **HTML**, the first web server, the first browser, and the first WYSIWYG editor [5].
* **The Scaling Bottleneck:** The Web grew exponentially, far beyond what Berners-Lee had originally anticipated [6]. The existing protocols and design mindsets were unable to scale to accommodate millions of concurrent users [6, 7].

### 2.2 Roy Fielding’s Architectural Solution (1993–2000)
* **1993:** Roy Fielding (co-founder of the Apache HTTP Server project) proposed a set of architectural constraints to make the World Wide Web scalable [7].
* **2000:** Fielding formalized these constraints in his landmark PhD dissertation, naming the architectural style **REST (Representational State Transfer)** [12]. He also co-authored the **HTTP 1.1** specification with Tim Berners-Lee to standardize these designs [11].

### 2.3 The 6 REST Constraints [7, 11]
To be considered truly "RESTful", an API must adhere to these core constraints:

1. **Client-Server Model:** Clear separation of concerns [7, 8]. The client handles the user interface and user experience (front-end), while the server handles data storage and business logic (back-end) [8]. This allows each side to evolve independently [8].
2. **Uniform Interface:** Establishes a standardized communication standard across all system components [8]. It consists of four sub-constraints:
   * *Resource identification* (e.g., URIs) [8]
   * *Resource manipulation through representation* [8]
   * *Self-descriptive messages* [8]
   * *Hypermedia as the engine of application state (HATEOAS)* [8]
3. **Layered System:** The architecture is arranged in hierarchical layers [9]. A layer can only see and interact with the immediate layer below it [9]. This allows intermediate layers (like load balancers, proxies, and caches) to be added without affecting the core system, greatly enhancing security and scalability [9].
4. **Cache:** Server responses must be explicitly labeled as cacheable or non-cacheable [9]. Caching reduces server loads, improves network efficiency, and enhances client perceived performance [9].
5. **Statelessness:** Each request from the client must contain *all* the information required to understand and process it [10]. The server does not store any client session context between requests [10]. This makes the system highly scalable and reliable since any server behind a load balancer can handle any incoming request [10].
6. **Code on Demand (Optional):** Servers can temporarily extend client functionality by sending executable code (such as JavaScript) [11]. Because it is optional, it is rarely a strict requirement for standard backend APIs [11].

## 3. What Does "REST" Actually Mean?
Roy Fielding’s term **Representational State Transfer** represents three fundamental concepts [12]:

* **Representational (R):** Resources (underlying database objects or data) can be represented in various formats depending on client/server needs [13]. For instance, a `user` resource might be represented as **JSON** for server-to-server APIs, or as **HTML** for a web browser [13, 14].
* **State (S):** State refers to the current condition, properties, or attributes of a resource at any given time (e.g., the items, quantities, and total price of a shopping cart) [15].
* **Transfer (T):** The movement of these resource representations between the client and server [16]. This transfer is performed using standard HTTP methods (such as `GET`, `POST`, `PUT`, `DELETE`, `PATCH`) [16].

## 4. Resource & URL Path Design
URLs are the entry points to REST resources. Well-designed paths should be intuitive, readable, and hierarchical [18, 38].

### 4.1 URL Anatomy
A standard API URL consists of:
`https://api.example.com/v1/books?limit=10`
* **Scheme:** `https://` (always use secure encryption in production) [19]
* **Subdomain (Authority):** `api.example.com` (industry standard is to use an `api.` subdomain) [19, 20]
* **Versioning:** `/v1/` or `/v2/` (highly recommended for backwards compatibility, usually embedded in the path) [20]
* **Resource Path:** `/books` (representing the resource) [20]
* **Query Parameters:** `?limit=10` (used for filtering, sorting, or pagination) [19]

### 4.2 Path Styling Rules
* **Plural Nouns Only:** Paths must represent resources as plural nouns, even when querying a single resource [21, 22].
  * ✅ Good: `GET /v1/books` (List books) [21]
  * ✅ Good: `GET /v1/books/:id` (Get single book) [22]
  * ❌ Bad: `GET /v1/book/:id` [22]
* **Lowercase Paths:** Keep all characters in lowercase to avoid case mismatch issues across different server/client OS environments [23, 24].
* **No Spaces or Underscores:** Use **hyphens** to separate words inside URL slugs or resource paths [23, 24].
  * Example: A book titled "Harry Potter" converts into a clean URL slug: `harry-potter` [23, 24].
* **Hierarchical Structure:** Use forward slashes (`/`) to signify relationships between parent and child resources [18, 24].
  * Example: `/organizations/:orgId/projects/:projectId/tasks` represents the hierarchical relationship: Organizations ➔ Projects ➔ Tasks [46, 80].

## 5. HTTP Methods and Idempotency
An operation is **idempotent** if performing the same action multiple times has the exact same side-effect as performing it once [25, 26].

| HTTP Method | Purpose | Idempotent? | Description / Side-Effects |
| :--- | :--- | :--- | :--- |
| **GET** | Retrieve data [27] | **Yes** [27] | It is a read-only fetch operation; it creates no changes (side-effects) in the server environment [28]. |
| **PATCH** | Partial update [29] | **Yes** [31] | Updates only specified fields in a resource (e.g., updating just the `status` field) [29, 31]. Repeatedly applying the same partial update results in the same state [31]. |
| **PUT** | Replace resource [29] | **Yes** [31] | Completely replaces the target resource with the client-supplied payload [29]. Subsequent identical requests produce the exact same final state [31]. |
| **DELETE** | Delete resource [32] | **Yes** [33] | Removes the target resource [32]. The first call deletes it; subsequent calls return `404 Not Found`, but cause no new side-effects on the server state [32, 33]. |
| **POST** | Create / Custom Action [33, 36] | **No** [33] | Used to create new resources (generating duplicates if repeated) [33, 35], or as an open-ended method for custom business actions [36, 37]. |

### 5.1 Custom Actions & POST
* **The Open-Ended Method:** In REST, `POST` is structurally open-ended [36]. It is utilized whenever an action cannot be neatly classified under standard CRUD operations [36, 37].
* **Examples of Custom Actions:**
  * Sending an email: `POST /v1/emails/send` [37]
  * Cloning a project: `POST /v1/projects/:id/clone` [93, 94]
  * Archiving an organization: `POST /v1/organizations/:id/archive` [79, 80]
* **Hierarchical Formatting:** Custom actions should follow a clean hierarchical path: `POST /resources/:id/action-name` [80].

## 6. Standard API Request/Response Guidelines

### 6.1 Status Codes
Using correct status codes helps client applications handle success and error states programmatically without guessing:

* **`200 OK`:** Success response for fetching (`GET`) or updating (`PATCH`/`PUT`) data [53, 71, 72].
* **`201 Created`:** Returned upon successful resource creation (typically `POST`). The response body should return the newly created resource with its database-generated metadata (`id`, timestamps) [52, 95].
* **`204 No Content`:** Returned upon successful deletion (`DELETE`). The response body is completely empty [73, 74].
* **`404 Not Found`:** Returned when the client requests a *specific single resource* (by ID) that does not exist or has been deleted [32, 74, 75].
  * *Important Rule:* Never return `404` for a list endpoint (`GET /resources`). If no records match query parameters/filters, return `200 OK` with an empty data array `[]` [75, 76].

### 6.2 Payloads and Data Formatting
* **Payload Consistency:** Fields should use identical names and formats across all endpoints [87]. If an organization uses `description`, projects should use `description` too (never abbreviate to `desc` or `dsc`) [87, 99, 100].
* **camelCase Standard:** Always format JSON payload keys and response properties using `camelCase` (e.g., `organizationId`, `createdAt`) [84].
* **Exclude Database Fields from Write Payloads:** Clients should never pass server-managed fields such as `id`, `createdAt`, or `updatedAt` in creation payloads; the server handles these fields automatically [51, 83].

## 7. Advanced List Capabilities: Pagination, Sorting & Filtering
When designing list APIs (e.g., `GET /organizations`), you must support pagination, sorting, and filtering via query parameters [62, 63, 67].

### 7.1 Pagination
* **Why Pagination is Mandatory:** In-memory serialization and network transfer of thousands of records is resource-heavy and introduces significant performance latency [54, 55]. Pagination allows the client to retrieve small, manageable chunks of data [56].
* **Query Parameters:**
  * `limit`: The number of items to return in a single page [59].
  * `page`: The page number of the slice of data requested [58, 59].
* **Standard Response Envelope Structure:**
  ```json
  {
    "data": [ ... ],       // Array of resources on the current page [57]
    "total": 5,            // Total number of resources in the database matching the query [57]
    "page": 2,             // Current page number [58]
    "totalPages": 3        // Total pages available based on the limit [58]
  }
  ```

### 7.2 Sorting
* **Query Parameters:**
  * `sortBy`: The field to sort by (e.g., `name`, `createdAt`) [63, 66].
  * `sortOrder`: The direction of the sort (e.g., `ascending`, `descending`) [63, 66].

### 7.3 Filtering
* **Query Parameters:** Allow clients to pass fields directly to filter the output:
  * Example: `GET /organizations?status=active` returns only active organizations [67, 68].

## 8. Summary of Best Practices for Backend Engineers
1. **Provide Sane Defaults:** Do not force clients to provide redundant parameters [64, 98]. If a parameter is missing, fall back to defaults:
   * Default `page` = `1` [60, 64]
   * Default `limit` = `10` or `20` [60, 64]
   * Default sorting = Sort by `createdAt` in `descending` order (newest first) [65]
   * Default entity status = Default to `active` upon creation if not provided [98, 99]
2. **Avoid Abbreviations:** Keep field names fully written and readable (e.g., use `description`, not `desc` or `dsc`) [99, 100].
3. **Be Consistent:** Follow a single, global standard across all your endpoints [89, 97]. If you choose a standard, stick to it. Consistency is the hallmark of a great API [89, 97].
4. **Interactive Documentation:** Integrate tools like **Swagger / OpenAPI** early to provide an interactive API playground and reliable documentation for consumers [96, 97].
5. **Requirements-Driven Resource Modeling:** Walk through wireframes or UI storyboards (e.g., in Figma) to extract the primary nouns [41, 42]. These nouns represent the resources of your backend [42, 43].
   * *Example:* A project management SaaS requirements analysis yields nouns like `organizations`, `projects`, `tasks`, `tags`, and `users` [43, 44].
